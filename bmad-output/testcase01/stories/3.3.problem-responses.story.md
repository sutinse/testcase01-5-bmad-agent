# 3.3: Yhtenäiset problem-virhevastaukset

**Story ID:** 3.3
**Epic:** 3 - Paikallisen simulaation turvaraja
**Slug:** problem-responses
**Status:** backlog

## Story

As a **API:n käyttäjä**,
I want **erottaa virhetilanteet sallituista liiketoimintatiloista**,
so that **odottaminen tai hylkäys ei näytä palveluvirheeltä**.

## Acceptance Criteria

1. Kaikkien kolmen reitin virheet palautuvat mediatyypillä `application/problem+json` ja yhteisillä `type`, `title`, `status`, `detail` sekä pyyntökorrelaation kentillä; JWT:tä, avainta tai koko asiakassyötettä ei vuoda.
2. Virheellinen syöte -> 400, puuttuva/virheellinen token -> 401, kielletty rooli/profiili/oma päätös -> 403, puuttuva tunniste -> 404, ristiriitainen uusinta/päätös -> 409 ja tallennusvirhe -> 5xx; oikeutettua olemassa olevan tilan lukua ei naamioida virheeksi.
3. `PENDING` ja `BLOCKED` vastaavat edelleen HTTP 200 JSON-tilavasteena `allowed=false`; virhesovitin ei muuta tallennettua päätöstä eikä muuta business-tilaa.

## Tasks / Subtasks

- [ ] Toteuta yhteinen virheiden ja frameworkin auth-virheiden sovitus RFC 7807 -runkoon (AC: #1, #2).
- [ ] Liitä kolmesta reitistä tulevat domain-virheluokat statuskoodeihin ilman varatiedon vuotoa (AC: #1, #2).
- [ ] Suunnittele jokaisen reitin virheiden mediatyyppitesti sekä PENDING/BLOCKED-kontrastit (AC: #1, #2, #3).

## Dev Notes

- HTTP 200 on myös odottavan ja hylätyn palautuksen hyväksytty tila; 400/401/403/404/409/5xx ovat erillisiä vikoja. [Source: architecture.md#adr-0018-erota-liiketoimintatila-http-virheestä]
- Problem-runko sisältää `type`, `title`, `status`, `detail` ja korrelaation, ei tokenia tai koko syötettä. [Source: architecture.md#api-specifications]
- Auth-virheiden kartoitus tehdään Quarkusin omilla hookeilla; testaa myös ennen resurssia syntyvä 401/403. [Inference]
